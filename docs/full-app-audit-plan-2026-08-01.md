## §B. 감사 원칙 6 — 이 코드베이스가 피로 배운 것을 방법론으로

1. **픽셀이 판정한다.** jsdom·DOM 프로퍼티·단위 테스트 초록은 판정이 아니다 — **바로 어제**
   `hidden` 속성을 `grid` 유틸리티가 덮어써서 "접힘"이 테스트 전부 초록인 채 화면엔 전부
   보이고 있었고, Playwright 스크린샷만이 잡았다. 모든 UI 판정은 실렌더 스크린샷+실측
   좌표(겹침·오버플로·줄바꿈은 좌표로 센다)로 한다.
2. **연결부터 의심한다.** 이 트랙의 지배 결함은 다섯 번 연속 "만드는 문제가 아니라 연결하는
   문제"였다(엔진 있는데 소비처 없음·두 소스 중 하나만 읽음·413줄 모듈 미호출). 존재 확인이
   아니라 **호출자 확인**: 모듈마다 "누가 부르나" grep, 데이터마다 "두 소스면 둘 다 읽나".
3. **주장은 재현 후에만 믿는다.** "미착수"를 일곱 번 틀리게 적었고, 티켓 숫자가 두 번 연속
   틀렸다. 문서·메모리·플랜의 모든 완료/미완료/수치 주장은 **5분 grep 재현**을 거쳐야
   원장에 오른다. 재현 불가면 "재현 불가"로 적지, 참으로 옮기지 않는다.
4. **잰 것만 사실이다.** 700KB 주장이 실측 423KB였다. 성능·크기·개수 문장엔 전부
   `[실측]`/`[계산]`/`[추정]` 태그를 달고, `[추정]`은 결론 근거로 못 쓴다.
5. **게이트 자체를 감사한다.** 게이트를 죽이는 건 코드가 아니라 그 옆의 것(주석 속 중괄호,
   `var()` 별칭→NaN 스킵, 생성 문서 손편집). 18개 상설 게이트 각각에 **뮤테이션 1방**
   (일부러 위반을 심고 빨간불 확인 후 원복)을 놓아 "아무것도 안 재면서 초록"을 색출한다.
6. **감사와 수정을 분리한다.** 발견 즉시 고치면 회귀·중복 수정·측정 오염이 생긴다.
   결함은 전부 §F-3 원장(재현 명령 포함)으로만 적재하고, 수정은 A8에서 원장 순서대로.
   예외는 **감사 진행 자체를 막는 블로커**뿐(고치고 원장에 "즉시수정" 표기).

## §C. 페이즈 A0~A8 — 순서와 이유

순서 논리: **카탈로그 → 회고 대조 → UI(눈) → 기능(손) → 연결(배선) → 성능(초시계) →
데이터·보안 → 원장 확정 → 수정.** UI가 먼저인 이유: 사장님 지시가 "UI부터"이기도 하고,
실렌더 스윕이 기능 결함(빈 데이터·에러 카드·깨진 상태)을 가장 싸게 노출하기 때문.

- P3(위생)는 사장님 결정: 지울지(죽은 코드) 살릴지(연결) — **자동 삭제 금지**(D10 계열).
- 종료 게이트: tsc 0 · jest 전체 green · build 0 · 18 게이트 green · A2 히어로 매트릭스
  재실행 → §P류 완주 원장 갱신 + 메모리 갱신.
