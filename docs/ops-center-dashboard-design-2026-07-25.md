# 관제센터 대시보드 — 설계안 (P2, 승인 전 구현 금지)

> 지시서 PHASE 3 요구: 각 모듈에 대해 **데이터 모델 / 화면 구성 / 배정 충돌 규칙 / MVP** 를 먼저 제안하고 승인받은 뒤 구현.
> 이 문서는 **설계안**이다. 승인 전까지 코드·마이그레이션 없음.

## 0. 코드 리얼리티 (추측 아님 — 라이브 DB·코드 확인 결과)

"현재 구현된 것 없음"이라는 전제와 달리, **하부 구조는 상당 부분 이미 존재한다.** 새로 만들 것과 조립할 것을 구분하는 게 이 설계의 핵심이다.

| 이미 있는 것 | 위치 | 상태 |
|---|---|---|
| `ops_guides` | 테이블 | 라이브 (가이드 1명) · PII 암호화 봉투(`rrn_enc`, `bank_account_enc`) 포함 |
| `ops_guide_assignments` | 테이블 | 라이브 — **가이드 배정의 뼈대가 이미 있음** |
| `ops_guide_unavailable_dates` | 테이블 | 라이브 — 근무 달력의 "불가일" 입력 |
| `ops_guide_rates` / `ops_guide_settlements` | 테이블 | 라이브 (정산 트랙) |
| `ops_room_vehicles` / `ops_vehicle_layouts` | 테이블 | 라이브 — **차량 배차의 뼈대** |
| `ops_seat_assignments` / `ops_tour_groups` | 테이블 | 라이브 |
| `tour_rooms` | 테이블 | 라이브 — 투어룸 생성 내역의 원천 |
| 관제 PWA 셸 | `components/tour-ops/OpsApp.tsx` | 라이브 (홈/대시보드/예약/지도/SOS/설정 6탭) |
| 배차 패널 | `components/tour-ops/OpsRoomVehiclePanel.tsx` | 라이브 |

→ **7개 모듈 중 5개는 "신규 개발"이 아니라 "기존 테이블 위의 화면 조립"이다.** 진짜 신규는 **배차 달력**의 충돌 판정과 **오토파일럿**뿐이다.

## 1. 모듈별 설계

### 1-1. 가이드 배정 (assignment)

- **데이터**: 기존 `ops_guide_assignments` 사용. 필요한 추가 컬럼만 additive로.
  - 필요: `status`(제안/확정/취소), `assigned_by`, `assigned_at`
- **화면**: 좌측 = 배정 대기 투어(날짜순), 우측 = 후보 가이드 리스트. 후보는 **자동 정렬**: ① 해당일 unavailable 아님 ② 언어 매칭(`ops_guides.languages` ∩ 예약 `preferred_language`) ③ 최근 배정 적은 순(부하 분산).
- **충돌 규칙 (핵심)**:
  1. **같은 가이드 · 같은 날짜 · 시간 겹침** → 하드 블록(저장 거부).
  2. `ops_guide_unavailable_dates`에 걸림 → 하드 블록.
  3. 언어 불일치 → **경고만**(가이드가 통역 동반 등 예외 존재).
  4. 하루 2건 이상 → 경고(연속 투어는 실제로 발생).
  - 하드 블록은 **DB 제약 + API 검증 둘 다**. UI 검증만 두면 동시 편집에서 뚫린다.
- **MVP**: 수동 배정 + 위 ①②만 하드 블록 + 배정 이메일 발송. 자동 추천 정렬은 v2.

### 1-2. 차량 배차 (vehicle dispatch)

- **데이터**: 기존 `ops_room_vehicles`. 차량 마스터가 없으면 `ops_vehicles`(신규, 최소: 번호판·좌석수·기사·활성) 필요.
- **화면**: 날짜 선택 → 그 날 투어 목록 × 차량 배정 상태. 좌석수 < 인원이면 즉시 빨간 표시.
- **충돌 규칙**: 같은 차량 · 같은 시간대 중복 → 하드 블록. 정원 초과 → 하드 블록(안전 문제).
- **MVP**: 차량 마스터 + 날짜별 배정 + 정원 검증.

### 1-3. 배차 달력 / 1-4. 가이드 근무 달력

- **하나의 컴포넌트, 두 개의 뷰로 만든다.** 축(가이드/차량)만 다르고 나머지는 동일 — 따로 만들면 두 번 유지보수해야 한다.
- **화면**: 월 그리드. 셀 = 그날 배정 건수 + 충돌 뱃지. 클릭 → 그날 상세.
- **데이터**: 신규 테이블 없음. 위 두 모듈의 조회 뷰.
- **MVP**: 읽기 전용 월 달력 + 충돌 하이라이트. 드래그 배정은 v2(모바일에서 드래그는 오조작 위험).

### 1-5. 월간 예약 내역 / 1-6. 투어룸 생성 내역

- **데이터**: `bookings`, `tour_rooms` 조회 전용. 신규 스키마 0.
- **화면**: 월 필터 + 상태 필터 + CSV 내보내기. 투어룸 내역은 `tour_rooms` × `tour_room_participants` 집계(참가자 수·마지막 활동).
- **MVP**: 목록 + 필터 + CSV. **이 두 개가 가장 싸고 즉시 유용하다 — 여기부터 하는 걸 권장.**

### 1-7. 오토파일럿 (autopilot)

- 가장 위험한 모듈. **"자동으로 배정/발송"은 잘못되면 손님에게 직접 노출된다.**
- **설계 원칙**: 오토파일럿은 **실행하지 않고 제안한다.** 제안 큐 → 사람이 승인 → 실행.
- **MVP 범위**: ① 미배정 투어 감지 ② 규칙 기반 가이드·차량 후보 제안 ③ 원탭 승인. **자동 실행은 MVP에서 제외.**
- 이유: 이 저장소의 이번 사고(광범위 자동 변경)와 같은 실패 모드다. 자동화의 이득보다 오배정 1건의 비용이 크다.

## 2. 권장 착수 순서

1. **월간 예약 내역 + 투어룸 생성 내역** (신규 스키마 0, 즉시 유용)
2. **가이드 배정** (테이블 존재, 충돌 규칙만 추가)
3. **차량 배차** (차량 마스터 신규)
4. **달력 2종** (위 3개의 뷰)
5. **오토파일럿** (제안 전용)

## 3. 인프라 항목

### 3-1. OTA 이메일 수신 주소 설정

- **데이터**: `ops_finance_config` 패턴을 따라 `ops_inbox_senders`(신규) — `{ id, address, channel, active, created_at }`. 또는 기존 설정 테이블에 JSON 키 하나.
- **화면**: 관제 설정 탭(`OpsSettingsTab.tsx` 존재)에 주소 목록 CRUD.
- **주의**: 수신 주소 화이트리스트는 **파싱 신뢰의 근거**가 되므로, 여기에 없는 발신자의 메일은 파싱 큐에 올리되 자동 확정하지 않는다.

### 3-2. 가이드 주소 암호화 키 — ⚠️ 새로 만들지 말 것

전수 확인 결과 **이미 확립된 암호화 봉투가 있다**: `lib/ops/guides/pii.ts`.

- **env 변수명**: `OPS_GUIDE_PII_ENC_KEY` (폴백 `GUIDE_PII_ENC_KEY`)
- **형식**: 아무 문자열이나 가능 — SHA-256으로 32바이트 파생 (`pii.ts:52-58`)
- **주소 필드도 이 키를 그대로 쓴다.** 별도 키를 만들면 봉투가 갈라지고 kursoflow 호환도 깨진다.
- **반영 위치**: Vercel 환경변수(Production + Preview). 로컬은 `.env.local`. **커밋 금지.**
- **현재 상태**: 라이브 `ops_guides`에 암호화된 데이터 **0건** → 지금 키를 넣는 것은 안전(기존 데이터 복호화 불능 위험 없음).
- ⚠️ **일단 설정한 뒤에는 절대 교체하지 말 것.** 교체 시 기존 `rrn_enc`/`bank_account_enc`/주소가 전부 복호화 불능이 된다.
- 주소 저장을 실제로 하려면 `ops_guides`에 `address_enc` / `address_masked` 컬럼 추가(additive)가 선행되어야 한다 — **현재 없음.**
