`lib/ops/autopilot/runner.ts:101`

```ts

.lte('tour_date', `${prevPeriod}-31`),   // ← 6월은 31일이 없다
```

## §C 속도 — 어디가 느린지 (근거: 실측)

### C1. 🔴 `ensureRoom`이 **읽기까지 쓰기로 만든다** — 가장 큰 구조적 낭비

`lib/tour-room/access.ts:138` — 조건 없는 `upsert`. **32개 라우트 · 72개 호출 지점**이 이걸 부르고,
GET 경로도 예외가 아니다.

증거: `tour_rooms`가 **insert 69 / update 1516**. 방은 69개 만들어졌는데 갱신은 1516번.
사실상 전부 읽기 요청이 만든 쓰기다.

이게 무는 비용:
1. 왕복 1회 추가 (그리고 `.select().single()`이라 결과까지 기다린다)
2. `updated_at`이 매번 바뀌므로 **`tour_rooms` 구독 Realtime이 읽기마다 발화**한다
3. WAL·복제 트래픽이 손님 폴링 수에 비례해 늘어난다
4. `seq_scan 2014 > idx_scan 1686` — booking_id로만 찾아야 할 테이블에 순차 스캔이 더 많다

**처방(C1-a):** `ensureRoom`을 **read-first**로. 있으면 그대로 반환, 없을 때만 insert,
`tour_id`/`tour_date`가 실제로 달라졌을 때만 update. 시그니처·반환은 그대로 두어
72개 호출부를 건드리지 않는다.
**처방(C1-b):** 순수 읽기 라우트는 `ensureRoom` 대신 `getRoom`(없으면 404)을 쓴다. 방이 없는데
GET을 하는 건 정상 상태가 아니다.

### C2. 손님 라우트 p90 1.1초 — 순차 왕복이 원인

`/extras` GET 실측 1029·1142ms. 안에서 벌어지는 일:

```
resolveRoomActor → booking 조회 → getAuthUser(GoTrue 원격 검증 가능) → 토큰 폐기 확인
→ ensureRoom(upsert)            → extras select
```

**4~5회 순차 왕복.** 서로 의존하지 않는 구간(토큰 폐기 확인 ↔ 방 조회)이 직렬로 붙어 있다.

**처방:** 독립 구간 `Promise.all` + C1과 합치면 GET은 2왕복으로 떨어진다. 목표 **p90 < 500ms**.

### C3. `/concierge` 3.7~5.7초

Tier1 LLM 응답이라 본질적으로 느리다. **이건 지연을 줄일 게 아니라 체감을 바꿔야 한다** —
스트리밍이 답이고, 라우트는 이미 `kind: 'tier1'`로 계층을 구분하고 있으므로 그 경계에 붙이면 된다.
⚠ Tier0(무네트워크)는 이미 즉답이므로 **건드리지 않는다.**

### C4. `/dining` — PR #464에서 46.4s → 15.8s. 남은 것은 제품 결정

동시성 4로 겹쳐 2.9배를 얻었다. 남은 ~16초를 없애려면 "코퍼스 완성 전에 손님에게 먼저 답한다"가
필요하고 그건 코드 결정이 아니다. **§F에 결정 대기로 올린다.**

### C5. 채팅 전송 1.2~2.0초

번역 팬아웃이 전송 응답에 물려 있다. 손님이 보낸 말이 화면에 뜨는 시점이 **번역이 끝난 뒤**다.
낙관적 큐가 클라이언트에 있으므로(TIER0 P1) 체감은 완화돼 있지만, 서버 응답 자체를
"저장 완료 → 즉시 200, 번역은 뒤이어 브로드캐스트"로 바꾸면 서버 시간이 1/3로 준다.
⚠ **번역 실패 시 조용히 원문만 남는 상태**를 만들면 안 된다 — 실패는 복구 라우트가 이미 있다(#417).

## §D 성능·부하 — DB 레벨

> 🔴 **이 절은 착수 후 전면 개정됐다.** 처음에는 어드바이저 297건을 그대로 줄 세워
> "미인덱스 FK 15건, 그중 투어룸 2건이 최우선"이라고 적었다. **틀렸다.**
> 실제 행 수를 재 보니 `tour_room_events` 2행, `tour_room_message_reactions` 0행이었다.
> 빈 테이블에 인덱스를 다는 것은 쓰기 비용만 늘린다. 어드바이저는 규모를 모른다 —
> **어드바이저를 정렬 기준으로 쓰면 안 되고, 정렬 기준은 실측이어야 한다.**

### D1 🔴 RAG 벡터 검색이 19MB HNSW 인덱스를 한 번도 안 쓰고 있었다 → **해결**

실측으로 드러난 이 DB의 최대 열원이다.

```
pg_stat_user_indexes  knowledge_chunks_embedding_hnsw   idx_scan = 0     (19 MB)
pg_stat_user_tables   knowledge_chunks   seq_scan 1561 · seq_tup_read 2,887,026
pg_stat_statements    이 RPC  mean 75ms × 1518콜 = DB 시간 118초
```

1120행짜리 테이블이 **56MB**인 이유는 행마다 1536차원 벡터가 붙어 있어서다.
매 질의가 그걸 전부 읽고 1120번 거리 계산을 했다.

**원인이 세 겹이었다.** 하나씩 벗겨야 보였다:

| # | 원인 | 확인 방법 |
|---|---|---|
| ① | `min_similarity`가 **거리식 자체에 걸린 잔여 필터** → ORDER BY 인덱스 경로 불가 | 이 술어만 빼면 즉시 Index Scan |
| ② | 후보 풀 24에서는 전수 스캔이 더 싸다고 계산됨 | `limit 8`은 인덱스, `limit 24`는 전수 |
| ③ | **SQL 함수 본문이 제네릭 플랜으로 캐시됨** — `limit $4`가 계획 시점에 값이 없다 | SET 절 세 번 다 실패, `execute…using`만 성공 |

**처방:** ANN을 먼저 끝내고 임계값을 밖에서 걸며, plpgsql `return query execute … using`으로
매 호출 실제 값으로 계획한다. 값은 전부 `USING`으로 넘어가므로 주입 표면이 없다.

```
원본                                buffers 16,969   391ms
+ enable_seqscan=off                buffers 12,084   (비트맵으로 바뀌었을 뿐)
+ ANN 먼저/임계값 나중               buffers 15,403   (함수 안에서는 변화 없음)
+ plan_cache_mode=force_custom_plan buffers 15,403   (변화 없음)
+ execute…using (최종)              buffers    892   ← 19배
```

**결과가 안 바뀌는 근거:** 브루트포스 상위 24와 이 함수의 상위 24를 대조 —
**id 목록과 순서가 완전히 동일**. 임계값을 넘는 행은 못 넘는 행보다 항상 더 유사하므로
"통과분의 상위 k"와 "상위 k 중 통과분"은 같은 집합이다. 적용 후 `idx_scan` 0 → 10.

⚠ 남은 한계: `p_locale`/`p_source_types`가 non-null이면 ANN 뒤 잔여 필터로 `match_count`보다
적게 올 수 있다(ANN+필터의 고전 문제). 지금 앱은 `p_locale=null`로만 부른다.

## §F-2 실기기 화면에서 나온 것 (사용자 제보 스크린샷 3장, 2026-07-26)

시뮬레이터가 못 잡고 **실기기 스크린샷이 잡은 것들**. 세 건 모두 §J-1과 같은 교훈이다 —
"구현은 다 돼 있는데 호출부/스코프가 비어 있다".

### F2-1 🔴 콕핏에 사진·파일 첨부가 없었다 → **수정함**
백엔드 `/messages` multipart는 처음부터 있었고 손님 컴포저는 쓰고 있었다. 콕핏만
**차량사진 하나**(고정 캡션)를 보낼 수 있었고 그 외에는 어떤 사진도 파일도 못 보냈다.

콕핏은 길가에서 한 손으로 쓴다. 고르면 바로 가고, 이미 입력된 문장이 캡션으로 따라간다.

### F2-3 🔴 명단 시트가 **투명하게** 떠서 채팅 위에 겹쳐 보였다 → 수정함

→ 같은 처방을 적용.

### F2-4 스태프가 손님 언어를 물려받는다 → 수정함
`TourRoomClient`는 join 결과의 `participant.locale`을 그대로 채택한다. 서버는 클라이언트가

기본값 500이 됐다. **7개 라우트 파일**이 인증 실패를 여기로 흘린다.

5xx는 모니터에겐 "서버가 고장났다"이고 클라이언트에겐 "재시도하라"인데, 진실은 "로그인하라"다.

#### W5-c 🔴 스윕이 한 번 **아무것도 안 물어보고 통과**했다

첫 실행은 "누출 0건 / 80라우트"를 보고했다. **160회 전부 404였다** — 경로에 `/api`를 두 번 붙였다.
`path.relative('app', …)`가 이미 `api/admin/…`인데 호출부가 `/api`를 또 붙인 것.
드러난 이유는 하나뿐이다: 401/403이 아닌 응답을 NOTE로 세고 **그 수를 출력했기 때문**이다.
→ 하니스가 이제 "401/403을 실제로 받았는가"를 **별도 검사로** 세고, 아니면 상태코드 분포를 찍는다.
**커버리지 하니스에서 가장 위험한 결과는 FAIL이 아니라 아무것도 안 물어본 PASS다.**

- **W6.2 채팅 전송 분리 — 착수하지 않음(연기).**

  🔴 **번역 실패가 조용해질 위험**이다. 이 저장소의 지배적 실패모드가 바로 그것이다.
  이득 대비 위험이 맞지 않는다. 하려면 "원문 브로드캐스트 → 번역 갱신"의 실패 표면을 먼저 설계할 것.
