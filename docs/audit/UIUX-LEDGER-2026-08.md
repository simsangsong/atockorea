## UX-000 — 🔴 오늘의 지배 결함 유형: **측정 실패가 합격처럼 생겼다**

앱 결함보다 먼저 적는다. **하루에 여섯 번 나왔고, 여섯 번 다 초록이었기 때문이다.**

| # | 도구 | 재려던 것 | 실제로 본 것 | 왜 안 보였나 |
|---|---|---|---|---|
| 1 | 성능 `qa-perf-idle` | 유휴 요청 수 | 방이 죽어도 **"0건" 초록** | 0이 정상 결과인 지표라 |
| 2 | 성능 `qa-perf-routes` | 라우트 속도 | 전 라우트 403 을 **"40ms 빠름"** 으로 | 응답 코드를 안 봤다 |
| 3 | 이 트랙 렌더 하니스 | 컨트롤 위반 | 예약 삭제된 DB 를 **"위반 0"** 으로 | 도달 단언이 없었다 |
| 4 | 이 트랙 C축 탐지기 | 형태 없는 로딩 | **가장 잘 아는 결함(UX-001)을 깨끗함**으로 | 파일 단위로 물었다 |
| 5 | 이 트랙 D축 판정기 | 하단 가구 높이 | `fixed` 를 찾다 **0px = 합격** | 결과가 아니라 **기법**을 찾았다 |
| 6 | 이 트랙 **인코딩 검사** | 한글 손상 | 한글 11,191자를 **"0자, 이상 없음"** 으로 | `grep -P` 부재 → `\|\| echo 0` 폴백 |

**6번이 가장 뼈아프다 — 감사자가 자기 산출물을 검증하는 도구였다.** 앞의 다섯은 앱을 쟀다.

### 세 갈래로 갈리는데 뿌리는 하나다

- **0을 합격으로 읽는다** (1·3·5·6) — 측정값이 0일 때 *측정 대상이 존재했다는 증거*를 따로 요구하지 않는다
- **넓은 조건은 틀려도 티가 안 난다** (2, 그리고 시뮬 cleanup 의 `contact_email` 폴백) —
  정리 세션의 문장이 정확하다: *"그 조건이 한 번도 실패한 적이 없어서 안 보였다."*
  목적이 끝난 폴백이 남아 매번 조용히 넓게 잡고 있었다
- **기법을 찾고 결과를 안 찾는다** (4·5) — "스켈레톤이 파일에 있는가" / "`fixed` 인가"를 물었다.
  물어야 했던 건 "그 기다림 옆에 형태가 있는가" / "바닥에 무엇이 얼마나 쌓였는가"였다

### 처방 (전부 적용됨)

1. **0을 보고할 땐 대상 존재를 따로 단언한다.** 렌더 하니스 `controls<5 && text<80자 → exit 2` ·
   인코딩 검사 `한글 0자 → exit 1` · 성능 `요청 0 + WS 0 → exit 1`
2. **뮤테이션은 양방향으로 잰다.** 깨뜨리면 빨강 **+ 정상이면 오탐 0**.
   한쪽만 보면 *"엄격해서 못 지나감"* 과 *"제대로 잡음"* 을 구분 못 한다.
   ✅ **U8 완료** — C축 탐지기에 대조군 두 벌을 심었다(아래)
3. **넓은 조건은 명시 플래그 뒤로.** 쓰이면 사람이 그렇게 결정한 것이 되게
4. **탐지기 안에 양성 대조를 심는다.** 성능 트랙이 자기 U+FFFD 검사에 넣은 형태 —
   *일부러 심은 손상을 잡는가*를 검사기 스스로 단언한다. 외부 뮤테이션과 다르다:
   뮤테이션은 사람이 돌려야 하고, 양성 대조는 **매 실행마다** 돈다
5. **천장은 그것이 지킬 코드에서 잰다.** 성능 트랙이 리베이스 이전 측정에서 뽑은 천장을 이후 코드에 걸었더니
   즉시 초과였고, 좁게 봤으면 **"회귀 발견"으로 보고했을 것**이다. 실제로는 게이트가 자기를 잡은 것이었다

### 5번은 이 원장에도 걸렸다 — 확인했다

C축 천장(우회 104 · 로딩 20)은 `a8dc24a8` 에서 쟀는데 그 사이 **main 이 22커밋 움직였고
`components/` 가 10파일 +730줄 바뀌었다**(신규 `RoomSeatSheet.tsx` 포함). **여유가 0** 이라 위험했다.

`origin/main` 머지 후 재측정: 스캔 **107 → 110**, 우회 **104 (천장 104 ✅)**, 로딩 **20 (천장 20 ✅)**.
새 컴포넌트가 우회도 형태 없는 로딩도 안 들여왔다. **버텼지만 운이 좋았다** —
여유 0 인 천장은 다음 머지에서 깨질 수 있고, 그때 **회귀처럼 보일 것**이다.
→ **머지할 때마다 재측정하고, 초과가 나오면 먼저 "내 코드인가 남의 코드인가"를 가른다.**

### 수렴 관찰 — 다른 세션이 독립적으로 같은 문장에 도달했다

머지로 들어온 `qa-smartapp-walk.mjs` 에 `checksRun` 카운터가 붙어 있었고, 주석이 이렇게 적혀 있다:

> *"an empty error list means 'nothing was wrong' and 'nothing was looked at' equally well"*

UX-000 을 모르는 채로 쓰인 문장이다. **세 트랙이 각자 같은 병을 만나 같은 처방에 도달했다** —
이 표가 개별 실수 모음이 아니라 **이 레포의 구조적 결함 유형**이라는 증거다.

이것이 §3 원칙 4(«통과는 증거가 아니다»)의 실제 사례집이다.
**감사 도구를 만들 때마다 이 표를 먼저 읽어라.**

### U8 — 양방향 대조군을 심었다 (2026-08-03)

처방 2번을 실제로 닫았다. `scripts/fixtures/uiux/` 에 답을 아는 파일 두 벌을 두고,
게이트가 **매 실행마다** 둘 다 확인한다:

| 대조군 | 파일 | 반드시 |
|---|---|---|
| **양성** | `dirty/BadCard.tsx` — hex 2 · raw 팔레트 2 · 형태 없는 로딩 1 | **잡혀야 한다** (bypass 4 · bare 1) |
| **음성** | `clean/GoodCard.tsx` — 토큰만 · 스켈레톤 옆 문구 | **조용해야 한다** (0 · 0) |

**뮤테이션과 다르다.** 뮤테이션은 사람이 기억해서 돌려야 하고, 대조군은 `npm run gate` 마다 돈다.

**양방향 확인:**
- 음성 대조를 오염시킴(`bg-[var(--tr-surface-2)]` → `bg-slate-200`) → **음성 테스트 빨강** = 오탐을 잡는다
- 양성 대조를 정상화(토큰화 + 스켈레톤 추가) → **양성 테스트 빨강** = 침묵한 탐지기를 잡는다

⚠ **픽스처를 `__tests__/` 밑에 두지 않았다.** `testMatch` 가 `**/__tests__/**/*.[jt]s?(x)` 라
거기 두면 jest 가 **테스트 스위트로 오인**하고 "must contain at least one test" 로 죽는다.
공용 `jest.config.js` 의 ignore 패턴을 건드리는 대신 `scripts/fixtures/` 로 옮겼다 —
그 설정은 FA-002 가 한 번 무너뜨린 자리라 남의 트랙 게이트를 흔들 이유가 없다.

## UX-001 — 가이드 콘솔: 빨리 뜨고, 1.8초 동안 아무 형태가 없다

**축:** R(응답성) 첫회 · C(일관성) 로딩 관용구 · **판정: 합격선 위반**

### 증상

| | 값 |
|---|---|
| FCP | **676 ms** |
| 첫 유의미(interactive) | **2,454 ms** |
| **그 사이** | **1,778 ms** |

그 1,778ms 동안 화면에 있는 것은 — `GuideConsole.tsx:482-486`:

```tsx
const preShell = (message: string) => (
  <div className={preShellDark ? 'dark' : ''}>
    <div className="tr-root tr-plan-root flex min-h-dvh items-center justify-center ...">
      <p className="tr-card-text text-[var(--tr-ink-2)]">{message}</p>
```

`GuideConsole.tsx:490` — `if (!overview) return preShell(error ? '접근할 수 없어요…' : '불러오는 중…')`

**화면 정중앙에 「불러오는 중…」 한 줄.** 스켈레톤도, 들어올 콘텐츠의 형태도 없다.

### 왜 이게 이 앱에서 가장 나쁜 모양인가

가이드 콘솔은 **빨리 뜨고 오래 안 된다** — 화면이 떴으니 눌러 보는데 반응이 없다.
손이 먼저 가고 앱이 안 따라온다. **가이드는 손님을 앞에 두고 이 화면을 연다.**

🔴 **초판에서 이 자리에 «손님 룸은 격차가 77ms 인데 가이드는 1,778ms» 라고 적었다. 그 비교를 뺐다.**
성능 트랙이 자기 계측의 한계를 알려 줬다 — **`첫 유의미` 는 라우트마다 셀렉터가 다르다**
(룸 `room-tabbar` · 가이드 `staff-shell`). **같은 종류의 사건이 아니므로 두 표면의 그 값을 빼서 쓰면 안 된다.**
77 과 1,778 은 각각 자기 앵커 기준이라 나란히 놓는 순간 앵커 차이가 결론에 섞인다.

**이 결함의 근거는 그 비교가 아니다.** 근거는 소스다 — `preShell` 이 **콘솔 전체를**
가운데 문자열 한 줄로 갈아치우므로, 그 창 내내 **누를 것이 하나도 없다**(U5 헛탭 0 이 이를 확인했다).
1,778ms 는 그 창의 크기를 말할 뿐 결론을 지탱하지 않는다.

⚠ **그리고 그 2,454ms 자체가 하한일 수 있다.** 성능 트랙의 `첫 유의미` 는 **셀렉터가 DOM 에 나타난 시각**이라
**"보이는데 안 먹는" 상태를 이미 도착으로 센다.** 실제 사용 가능 시각은 그보다 늦을 수 있고,
그 구간은 그쪽 계측이 구조적으로 못 본다.

### 두 합격선을 동시에 위반한다

- **UX-D8 (R 첫회):** 100ms 안에 **형태**가 보여야 한다. 문자열은 형태가 아니다.
- **UX-D6 (C 로딩 관용구):** **문자열 단독 금지.** 문구는 스켈레톤에 덧붙이는 것이지 그 자체가 상태 표현이 아니다.

### 이 결함이 어떻게 발견됐는가 🔴

**어느 한쪽 트랙만으로는 못 찾는다.**
성능 트랙의 숫자는 "2,454ms 만에 쓸 수 있게 된다"까지만 말한다 — 그건 성능 진술이다.
소스 읽기는 "로딩 중엔 문자열 한 줄"까지만 말한다 — 그것만으론 1.8초인지 50ms인지 모른다.
**둘을 겹쳐야 "1.8초 동안 형태가 없다"가 된다.** 두 트랙을 나눈 경계(UX-D7 "얼마나 / 그동안 무엇이")가
첫날부터 값을 했다.

### ✅ U9 수정 완료 (2026-08-03)

`preShell` 은 **세 상태**를 다 같은 문자열로 그리고 있었다 — 토큰없음 · 에러 · 로딩.
**로딩만** 형태를 받고 나머지 둘은 문구를 유지한다(원장이 미리 적어 둔 함정 그대로 —
**에러에 스켈레톤을 씌우면 영원히 로딩 중인 화면**이 된다).

**콘솔이 될 모양**을 먼저 보여 주고, 문구는 그 안에 status 로 얹는다.

**실측 검증:**

|---|---|---|---|

| 에러(403) | **없음** ✅ | **0** ✅ | 「접근할 수 없어요 — 링크를 다시 확인해 주세요.」 |

**탐지기가 놓아줬다:** C-2 `bareLoading` **20 → 19파일**, `GuideConsole` 해제.
**게이트 천장도 같은 커밋에서 20 → 19 로 내렸다**(여유를 남기면 다음 회귀의 자리가 된다).

🔴 **가드를 지우지 않고 뒤집었다.** 「UX-001 이 잡히는가」를 단언하던 테스트는 수정과 함께 실패하기 시작했다.
지우면 회귀 가드를 버리는 것이므로, **「UX-001 이 계속 고쳐져 있는가」로 반전**했다 —
스켈레톤을 다시 떼면 빨개진다(뮤테이션 확인). 그 테스트가 원래 지키던 것(탐지기가 근접 판정을 유지하는가)은
**양성 대조군**이 이어받는다. 대조군은 거리의 우연으로 만족시킬 수 없다.

## UX-009 — 매 로드마다 가이드에게 「링크가 잘못됐다」고 먼저 말한다 · ✅ U9 수정

**축:** R · S6(신뢰) · **U9 수정 중 발견** — 스켈레톤을 검증하려고 로딩 창을 붙잡았더니 드러났다.

**증상 (실측, dev):**

| 시각 | 화면 |
|---|---|
| ~400 ms | **「가이드 링크(이메일의 버튼)로 접속해 주세요.」** ← 링크는 멀쩡하다 |
| 이후 | 「불러오는 중…」 |

**원인:** `useState<string | null>(null)` — **초기값 `null` 이 "토큰 없음"과 "아직 안 읽음"을 같은 것으로
취급**한다. 토큰은 `useEffect` 에서 읽으므로 첫 페인트에는 언제나 `null` 이고, 렌더는 그걸
**"링크가 틀렸다"** 로 번역했다. **모든 로드가 사용자를 탓하며 시작한다.**

🔴 **풀 오디트가 목록으로 만든 fail-open 3형제와 같은 모양이다** — *"없음"과 "확인 실패"를 같게 취급*.
여기선 결과가 보안이 아니라 **신뢰**다. 하지 않은 실수로 지목당하는 건 빈 화면보다 나쁘다.

**수정:** `useState<string | null | undefined>(undefined)` — `undefined` = 아직 안 읽음(→ 스켈레톤) ·
`null` = 읽었고 없음(→ 문구). `useTourManifest` 에는 `token ?? null` 로 넘긴다(그 훅에겐 둘이 같은 답).

**검증:** 6프레임 연속 스켈레톤, **「가이드 링크」 문구 0회 등장.**

**재현(수정 전):** 로딩을 붙잡고 250ms 부터 프레임을 찍으면 첫 프레임에 그 문구가 잡힌다.

손님 홈의 13개 중 배경이 있는 건 4개(전부 `rgb(252,252,251)` 근백색), 나머지 9개는 완전 투명이다.
**스태프 표면은 위계가 있고 손님 표면은 없다.** G-f("타일 7개 중 5개가 동일한 차콜")가
파스텔 팔레트로 바뀌었을 뿐 병은 그대로다.

🔴 **합격선을 「≤1」에서 「정확히 1」로 고쳤다**(UX-D12). primary 가 없는 화면은 셋 있는 화면만큼 나쁘다 —
전자는 이 계측 없이는 **초록으로 보인다.**

**관제도 0이다** — 컨트롤 18개 중 accent 배경 **0개**. UX-D3 에서 관제를 「C+H 두 축」으로 잡은 판단이
여기서 값을 했다. **일관성 축만 봤으면 이 화면은 통과했을 것이다** — 토큰은 잘 쓰고 있고, 잘림도 0이고,
하단 가구도 8% 다. **문제는 "규칙을 어겼다"가 아니라 "아무것도 이기지 않는다"** 이고,
그건 위계 축으로만 보인다. G-l(SOS 가 룸 개수와 같은 무게)이 같은 병의 더 심한 형태다.

#### 🔴 관제는 두 트랙이 같은 화면에 도달했다 — U9 에서 같이 잡는다

성능 트랙이 감사를 닫으며 관제를 **`tour-ops` 한 페이지 문제**로 좁혔다:
**199 KB**(2위의 3.2배) · **TBT 848~1,214ms**(전 표면 최악) · **패널 36개 전부 정적 import**.

**내 «accent 0개» 와 같은 화면이다.** 겹치면 이렇게 된다 —
**눌러야 할 게 뭔지 안 보이는데, 눌러도 0.85~1.2초 동안 안 먹는 화면.**
각각은 중간 심각도인데 겹치면 다르다.

⚠ **동적 import 를 처방으로 먼저 쓰지 말 것.** 성능 트랙이 룸에서 그 분리를 **실제로 해 봤고**
결과는 *"Real, and small"* — 782 → 746 KB, FCP 5,892 → 5,808ms. **36개 패널이라는 사실이
처방을 결정하지 않는다.** TBT 848ms 가 파싱인지 실행인지 렌더인지부터 프로파일해야 한다.

**이 트랙이 이미 두 번 배운 것과 같은 형태다** — UX-D5(44px 을 한 번에 올리지 않고 먼저 센다) ·
190 hex 중 84 가 풍경화. **숫자가 크다는 사실은 원인이 아니다.**

실측 **172px = 20%**(컴포저 블록 115 + 탭바 57). G-g 가 적은 330px 은 `#548`(스마트가이드 카드 제거) 이전 값이다.

오발신 위험을 무릅쓰고 시그널·퀵리플을 합칠 이유가 없다.

### ✅ P축은 깨끗하다 — 그리고 소스의 43은 결함이 아니었다

네 표면 전부 **44px 미만 히트 타깃 0**. U2 가 소스에서 센 40~43px 지정 **43건**은
**"렌더로 확인할 후보 상한"이라고 적어 둔 그대로**였다 — 실제 히트 타깃이 아니었다.
(다른 상태·표면에서 다시 볼 것. 지금 결론은 "이 네 화면엔 없다"이지 "앱에 없다"가 아니다.)

### 🔴 이 계측기는 다섯 번 틀린 뒤에 맞았다

D축 하나가 다섯 판을 갔고, **매번 다른 방향으로 틀렸다.** 기록해 둔다 — 다음 계측기도 그럴 것이기 때문이다.

| 판 | 규칙 | 보고한 값 | 무엇이 틀렸나 |
|---|---|---|---|
| 1 | `position: fixed/sticky` 를 찾는다 | 손님 **0px** | 이 앱엔 fixed/sticky 가 **하나도 없다.** 하단 스택은 **플렉스**로 만든다 — 결과가 아니라 **기법**을 찾았다 |
| 2 | 뷰포트 바닥에 붙은 요소 | 채팅 **57px** | 탭바만 봤다. 컴포저는 바닥이 787 이라 안 걸린다 |
| 3 | 위로 체이닝 | 전 표면 **100%** | 본문 영역(`tr-atmos h=735`)까지 삼켰다 |
| 4 | 요소 높이 30% 상한 | **35%** | 풍경화 SVG 의 `<path>` 한 조각(h=240)을 가구로 셌다 |
| 5 | SVG·아트 레이어 제외 | **7 / 20 / 7 / 31%** | ✅ |

**1판이 가장 위험했다** — 0px 은 «합격»으로 보인다. 도달 단언이 없었다면 그대로 초록으로 넘어갔다.
그리고 **4판의 오탐은 C축이 이미 가르쳐 준 것과 같은 것**이었다(190 hex 중 84가 풍경화).
**아트 레이어는 축이 바뀌어도 계속 끼어든다.**

🔴 **그리고 이 하니스는 한 번, 예약이 사라진 DB 를 상대로 "컨트롤 13개 · 위반 0"을 보고했다.**
화면엔 「해당 정보의 예약을 찾을 수 없습니다」가 떠 있었다. 도달 단언(`controls < 5` → unreachable, exit 2)을
넣은 이유다. **0 을 보고하는 게 가장 위험한 실패다.**

### ⚠ 시뮬은 공유 자원이다

측정 중 시뮬 예약 3건이 **DB 에서 사라졌다**(`sim_tag` 행 0). `sim-tour-day.ts --cleanup` 은

성능 트랙과 동시에 돌릴 수 없다 — **시딩 전에 알리는 것이 규칙이어야 한다.**

## UX-008 — 식당을 세 번 고르면 벽이다. 그런데 앱은 "다시 시도하세요"라고 말한다

**축:** R(응답성) · H(위계) · **판정: 서버가 보낸 답을 앱이 버린다**

### 발단 — 성능 트랙이 사고로 발견했다

하니스가 3초 간격 5회를 눌렀더니 **5/5 가 429**. 원인은 의도된 설계다(MISS 가 유료 외부 API):

```ts
// app/api/tour-rooms/[bookingId]/dining/route.ts:95-103  [코드 실측]
requestGate({ namespace: 'tour_room_dining',      key: gateKey,               perMinute: 3, perHour: 20 })
requestGate({ namespace: 'tour_room_dining_room', key: `booking:${id}`,       perMinute: 6, perHour: 40 })
…
return NextResponse.json({ error: 'rate_limited' },
  { status: 429, headers: { 'Retry-After': String(Math.ceil(retryAfterMs / 1000)) } });
```

**참가자 3회/분.** 그런데 **손님이 식당을 고르는 행동은 원래 여러 번 눌러보는 것**이다 —
「점심 추천」 → 별로네 → 다시 → 또 별로 → 다시. **세 번이면 벽이다.**

### 🔴 결함은 리밋이 아니라 리밋을 말하지 않는 것이다

**서버는 언제 다시 되는지 계산해서 `Retry-After` 로 보낸다. 손님 앱은 그걸 읽지 않는다.**

| 파일 | `429` | `rate_limited` | `Retry-After` |
|---|---|---|---|
| `BriefingLunchCard.tsx` | 0 | 0 | 0 |
| `ConciergePanel.tsx` | 0 | 0 | 0 |
| `DiningCard.tsx` | 0 | 0 | 0 |
| `ChatFeed.tsx` | 0 | 0 | 0 |

앱 전체에서 `Retry-After` 를 읽는 곳은 **마케팅 사이트의 AI 위젯 하나뿐**이다(`TourProductAiAssistantWidget.tsx`).
**스마트앱에는 없다.**

그래서 429 는 일반 실패 경로로 떨어지고, 손님이 보는 것은 `ConciergePanel.tsx:135` 의 그 문구다:

> **「문제가 발생했어요 — 다시 시도하거나 가이드에게 물어보세요.」**

**다시 시도가 정확히 차단된 상태에서 다시 시도하라고 말한다.** 그리고 언제 풀리는지는
**서버가 알고 보냈는데 앱이 버렸다.**

### 이 트랙의 지배 결함 유형 그대로다

**엔진은 있고 소비처가 없다.** `Retry-After` 는 계산되고 전송된다 — 아무도 안 읽을 뿐이다.
단위 테스트로는 안 잡힌다: 라우트 테스트는 헤더가 나가는 걸 확인하고, 컴포넌트 테스트는
그 헤더를 모른다. **결함은 둘 사이에 있다.**

### UX-002 와 겹쳐서 더 나빠진다

UX-002 는 «13초 뒤 실패인데 재시도 버튼이 없다» 였다. UX-008 은 그 실패가 **rate limit 일 때**
같은 문구가 **거짓말이 된다**는 것이다. 그리고 U5 가 잰 대로 **컨시어지는 홈에서 1탭**이다.

### 재현

```
node scripts/qa-perf-dining.mjs --hit 5 --gap 3000     # 5/5 가 429 (성능 트랙 하니스)
sed -n '92,104p' "app/api/tour-rooms/[bookingId]/dining/route.ts"
grep -ci 'retry-after' components/tour-mode/*.tsx      # 전부 0
grep -rli 'retry-after' components/                     # 마케팅 위젯 하나뿐
```

### ✅ U9 수정 완료 (2026-08-03) — UX-002 와 한 덩어리로

선행 조건부터 놓았다. `ThreadEntry.failure = { kind, retryAfterSec, retryAtMs, question }` —
**무엇이 실패했는지와 무엇을 물었는지**를 담을 자리다. 이게 없어서 패널은 429 를 다른 실패와
구분할 수도, 재시도를 제안할 수도 없었다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 429 응답 | 일반 실패로 떨어짐 | **`Retry-After` 를 읽어** 「Too many requests — try again in 42s.」 |
| 재시도 | **없음** (질문을 다시 타이핑) | 버튼 1탭 — 저장해 둔 질문을 재전송 |
| 리밋 중 버튼 | — | **비활성 + 남은 초 카운트다운**(`Try again · 40s`) |

🔴 **첫 판에서 «반드시 실패하는 버튼»을 만들 뻔했다.** 429 에도 활성 버튼을 달았는데,
그건 **UX-008 이 지적한 바로 그 결함이 문장 대신 버튼을 입은 것**이다 —
누를 수 없는 순간에 누르라고 권한다. 리밋이 남아 있는 동안 비활성 + 카운트다운으로 바꿨고,
틱은 그런 실패가 실제로 걸려 있을 때만 돈다.

**실측 검증 (라우트 목킹, 실렌더):**

| 시나리오 | 버튼 | 비활성 | 라벨 | 탭 시 재요청 |
|---|---|---|---|---|
| 429 + `Retry-After: 42` | 1 | **true** ✅ | `Try again · 40s` | **0** (막힘) ✅ |
| 500 | 1 | false | `Try again` | **1** ✅ |

**판정 근거였던 두 grep 이 뒤집혔다:** 재시도 어포던스 **0 → 10** · `Retry-After` **0 → 3**.

문구는 `CONCIERGE_RETRY_COPY` 로 **10로케일 한 블록**에 넣었다 —
기존 로케일 표 열 곳을 각각 고치면 편집 지점이 열 개고, 그중 하나만 틀려도 그 로케일만 조용히 깨진다.

### 🔴 UX-011 — 서랍 검색 결과의 시각이 **기기 로케일·기기 타임존**으로 찍힌다 (수정함)

영어 방(상품명·라벨·역할 전부 영어)의 검색 결과에만 **「오후 08:00」** 이 한국어로 찍혔다.
원인은 `RoomDrawer.tsx` 의 `toLocaleTimeString([], …)` — `[]` 는 브라우저 기본값,
즉 **기기 로케일 + 기기 타임존**이다.

로케일보다 **타임존이 더 나쁘다**: 폰이 아직 고향 시간대인 손님은 **검색 결과의 시각과,
그것을 눌러 도착한 말풍선의 시각이 서로 다르게** 보인다.

이 레포의 전형적 결함 모양이다 — **있는 것을 새 소비처가 안 읽었다.**
`lib/tour-room/timeFormat.ts` 의 `formatBubbleTime(iso, locale)` 이 정확히 이 일을 하고
`ChatFeed` 는 그걸 쓴다. PR #715 의 서랍 검색만 우회했다.
→ `formatBubbleTime` 으로 교체. **실렌더 재확인: 기기 `ko-KR` · 방 `en` → 「1:41 AM」.**
게이트 `__tests__/audit/deviceLocaleLeak.test.ts` 신설(빈 로케일 인자 금지, 뮤테이션 포함).

### 🔴 UX-012 — 「전체 공지로 재전송」이 눌러도 화면에 아무 말이 없다 (미수정)

동작은 정상이다(201, delivered 1/1, 메시지 생성 확인). 그런데 **토스트도, 배너도, 상태 변화도 없다.**
`TourRoomClient.tsx` 의 `void fetch('/api/tour-rooms/broadcast', …)` 는 **fire-and-forget** 이라
성공도 실패도 화면에 나타나지 않는다 — 즉 **진짜 실패했을 때와 성공했을 때가 구분되지 않는다.**
전 손님에게 나가는 되돌릴 수 없는 팬아웃 액션이다. 처방(토스트/낙관적 캡슐/에러 표시)은 UI 결정이라 남긴다.

⚠ **핸드오프 §1 의 「NoticeBanner 반영」은 기대가 틀렸다.** 승격은 `kind:null` 인 가이드 메시지를 만들고,
`NoticeBanner` 는 `meeting_notice`/`free_time_timer` 만 읽는다(`latestNoticeMessage`). 배너는 원래 안 뜬다.

### 🔴 UX-013 — 손님 채팅에 React key 경고가 상시 뜬다 (원인 미특정)

`/tour-mode/room/[bookingId]` 채팅 탭에서 매번:
`Each child in a list should have a unique "key" prop. … It was passed a child from ChatFeed.`
채팅 피드에서 key 가 어긋나면 **DOM 재사용이 엉켜 엉뚱한 말풍선에 내용이 붙을 수 있다** — 경고 이상의 위험이다.

**아닌 것으로 확인한 것들**(추측 대신 측정): DOM 의 `data-msg-id` **30개 전부 유일**(중복 0) ·

여기서 멈췄다.
**재현:** 룸 열기 → 채팅 탭 → 콘솔. 다음 세션이 `lib/` 헬퍼나 tour-mode 밖 컴포넌트를 좁히면 된다.
