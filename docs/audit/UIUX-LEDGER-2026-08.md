## UX-001 — 가이드 콘솔: 빨리 뜨고, 1.8초 동안 아무 형태가 없다

**축:** R(응답성) 첫회 · C(일관성) 로딩 관용구 · **판정: 합격선 위반**

### 증상

| | 값 |
|---|---|
| FCP | **676 ms** |
| 첫 유의미(interactive) | **2,454 ms** |
| **그 사이** | **1,778 ms** |

그 1,778ms 동안 화면에 있는 것은 — `GuideConsole.tsx:482-486`:

```tsx
const preShell = (message: string) => (
  <div className={preShellDark ? 'dark' : ''}>
    <div className="tr-root tr-plan-root flex min-h-dvh items-center justify-center ...">
      <p className="tr-card-text text-[var(--tr-ink-2)]">{message}</p>
```

`GuideConsole.tsx:490` — `if (!overview) return preShell(error ? '접근할 수 없어요…' : '불러오는 중…')`

**화면 정중앙에 「불러오는 중…」 한 줄.** 스켈레톤도, 들어올 콘텐츠의 형태도 없다.

### 왜 이게 이 앱에서 가장 나쁜 모양인가

손님 룸은 FCP 2,832 → 첫 유의미 2,909 로 **격차가 77ms** 다. 늦게 뜨지만 뜨면 바로 된다.
가이드 콘솔은 **빨리 뜨고 오래 안 된다.** 후자가 사람에게 더 나쁘다 —
화면이 떴으니 눌러 보는데, 1.8초 동안 반응이 없다. 손이 먼저 가고 앱이 안 따라온다.

**가이드는 손님을 앞에 두고 이 화면을 연다.** 대기 비용이 손님 룸보다 비싸다.

### 두 합격선을 동시에 위반한다

- **UX-D8 (R 첫회):** 100ms 안에 **형태**가 보여야 한다. 문자열은 형태가 아니다.
- **UX-D6 (C 로딩 관용구):** **문자열 단독 금지.** 문구는 스켈레톤에 덧붙이는 것이지 그 자체가 상태 표현이 아니다.

### 이 결함이 어떻게 발견됐는가 🔴

**어느 한쪽 트랙만으로는 못 찾는다.**
성능 트랙의 숫자는 "2,454ms 만에 쓸 수 있게 된다"까지만 말한다 — 그건 성능 진술이다.
소스 읽기는 "로딩 중엔 문자열 한 줄"까지만 말한다 — 그것만으론 1.8초인지 50ms인지 모른다.
**둘을 겹쳐야 "1.8초 동안 형태가 없다"가 된다.** 두 트랙을 나눈 경계(UX-D7 "얼마나 / 그동안 무엇이")가
첫날부터 값을 했다.

### 재현

```
# 시간 (성능 트랙 하니스)
WALK_BASE=http://localhost:<port> node scripts/qa-perf-throttled.mjs --profile 4g --runs 3 --out
#   조건: 프로덕션 빌드 + next start · 390×844 · 콜드 캐시 · 3회 중앙값 · 4G(4Mbps↓/RTT 70ms/CPU 4x)
#   정본: docs/audit/PERF-THROTTLED-4g.md (perf 트랙 커밋 3d3d128c)

# 그 사이에 무엇이 있는가 (소스)
sed -n '482,490p' components/tour-mode/guide/GuideConsole.tsx
```

### 수정 아님 — U9 후보

고칠 때 건드릴 자리는 `preShell` 하나다. 다만 **`preShell` 은 에러 메시지도 그린다**(`접근할 수 없어요`) —
에러에 스켈레톤을 씌우면 영원히 로딩 중인 화면이 된다. **로딩과 에러를 갈라야** 한다.

## UX-002 — 컨시어지: 13초를 치르고 실패했는데, 「다시 시도」할 것이 없다

**축:** R(응답성) · H(위계) · **판정: 합격선 위반 + 문구가 지키지 못하는 약속**

### 증상

성능 트랙 P-07: 질문 → 답변 **9~13초**(예산 2~3배), **게다가 실패**.
원인은 그쪽 원장에 있다(라우터 타임아웃 8s × 공급자 2 vs 예산 4s). **여기서는 그 13초가 손님에게 어떻게 보이는가만 본다.**

| 구간 | 손님이 보는 것 | 소스 |
|---|---|---|
| 0 → 13초 | `<span>확인 중…</span>` **문자열 한 줄** | `ConciergePanel.tsx:286` |
| 13초 | 「문제가 발생했어요 — **다시 시도하거나** 가이드에게 물어보세요.」 | `concierge.ts:201` |
| 그 다음 | **누를 것이 없다.** 질문을 다시 타이핑해야 한다 | 재시도 어포던스 **0건** |

### 🔴 진짜 결함은 문구가 아니라 문구가 지키지 못하는 약속이다

**실패 문구 자체는 잘 쓰였다.** 실패를 숨기지 않고, 다음 행동 둘(재시도 · 가이드에게)을 준다 —
A8 감사가 S5(회복력)를 올린 그 작업의 결과다.

**그런데 「다시 시도」할 버튼이 없다.** `grep -cE 'retry|다시 시도|재시도' ConciergePanel.tsx` → **0**.
13초를 기다린 손님에게 "다시 시도하세요"라고 말하면서 **다시 시도하는 방법은 타이핑을 처음부터**다.
투어 중, 걸으면서, 한 손으로.

### 곁가지 — 실패가 정상 답변과 같은 모양으로 들어간다

`ConciergePanel.tsx:140` — `push('assistant', copy.error)`.
`ThreadEntry` 는 `{ id, role: 'user' | 'assistant', text, mapCard?, diningCard? }` 로 **에러 플래그가 없다.**
실패는 **일반 어시스턴트 버블**로 렌더된다.

⚠ **이걸 단독 결함으로 올리지 않는다.** 채팅 UI 가 시스템 메시지를 버블로 주는 건 정당한 관용구이고,
문구가 스스로 실패라고 밝힌다. 다만 **재시도 버튼을 붙이려면 이 플래그가 먼저 필요**하므로 같이 적어 둔다.

### 재현

```
# 시간 (성능 트랙)
node scripts/qa-perf-interactions.mjs --runs 10     # P-07
# 무엇이 보이는가 (소스)
sed -n '284,290p;138,142p' components/tour-mode/ConciergePanel.tsx
grep -n "thinking:\|error:" lib/tour-room/concierge.ts
grep -cE 'retry|다시 시도|재시도' components/tour-mode/ConciergePanel.tsx   # → 0
```

## UX-003 — 패턴: 기다림을 문자열로 때우는 것이 이 앱의 기본형이다

**축:** C(일관성) · **판정: UX-D6 위반이 산발이 아니라 기본형**

두 건이 독립적으로 같은 모양이었다:

| | 기다림 | 그 동안 보이는 것 |
|---|---|---|
| UX-001 가이드 콘솔 | 1,778 ms | `<p>불러오는 중…</p>` |
| UX-002 컨시어지 | 9,000~13,000 ms | `<span>확인 중…</span>` |

**두 번이면 우연이지만, 인구조사가 이미 셋을 말하고 있었다** — 스켈레톤 13파일 · 스피너 15 · **로딩 문자열 21**.
문자열이 **최다 관용구**다. UX-D6(«스켈레톤이 기본, 문자열 단독 금지»)은 소수를 다수로 바꾸는 결정이다.

🔴 **U3 이 이걸 표면별로 세어야 한다.** 지금 숫자(21파일)는 **소스 기준이라 상한**이다 —
그중 몇 개가 실제로 500ms 넘는 기다림에 걸리는지는 렌더만 안다. 190 hex 중 84가 SVG였던 것과 같다.
