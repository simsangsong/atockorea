## UX-001 — 가이드 콘솔: 빨리 뜨고, 1.8초 동안 아무 형태가 없다

**축:** R(응답성) 첫회 · C(일관성) 로딩 관용구 · **판정: 합격선 위반**

### 증상

| | 값 |
|---|---|
| FCP | **676 ms** |
| 첫 유의미(interactive) | **2,454 ms** |
| **그 사이** | **1,778 ms** |

그 1,778ms 동안 화면에 있는 것은 — `GuideConsole.tsx:482-486`:

```tsx
const preShell = (message: string) => (
  <div className={preShellDark ? 'dark' : ''}>
    <div className="tr-root tr-plan-root flex min-h-dvh items-center justify-center ...">
      <p className="tr-card-text text-[var(--tr-ink-2)]">{message}</p>
```

`GuideConsole.tsx:490` — `if (!overview) return preShell(error ? '접근할 수 없어요…' : '불러오는 중…')`

**화면 정중앙에 「불러오는 중…」 한 줄.** 스켈레톤도, 들어올 콘텐츠의 형태도 없다.

### 왜 이게 이 앱에서 가장 나쁜 모양인가

손님 룸은 FCP 2,832 → 첫 유의미 2,909 로 **격차가 77ms** 다. 늦게 뜨지만 뜨면 바로 된다.
가이드 콘솔은 **빨리 뜨고 오래 안 된다.** 후자가 사람에게 더 나쁘다 —
화면이 떴으니 눌러 보는데, 1.8초 동안 반응이 없다. 손이 먼저 가고 앱이 안 따라온다.

**가이드는 손님을 앞에 두고 이 화면을 연다.** 대기 비용이 손님 룸보다 비싸다.

### 두 합격선을 동시에 위반한다

- **UX-D8 (R 첫회):** 100ms 안에 **형태**가 보여야 한다. 문자열은 형태가 아니다.
- **UX-D6 (C 로딩 관용구):** **문자열 단독 금지.** 문구는 스켈레톤에 덧붙이는 것이지 그 자체가 상태 표현이 아니다.

### 이 결함이 어떻게 발견됐는가 🔴

**어느 한쪽 트랙만으로는 못 찾는다.**
성능 트랙의 숫자는 "2,454ms 만에 쓸 수 있게 된다"까지만 말한다 — 그건 성능 진술이다.
소스 읽기는 "로딩 중엔 문자열 한 줄"까지만 말한다 — 그것만으론 1.8초인지 50ms인지 모른다.
**둘을 겹쳐야 "1.8초 동안 형태가 없다"가 된다.** 두 트랙을 나눈 경계(UX-D7 "얼마나 / 그동안 무엇이")가
첫날부터 값을 했다.

### 재현

```
# 시간 (성능 트랙 하니스)
WALK_BASE=http://localhost:<port> node scripts/qa-perf-throttled.mjs --profile 4g --runs 3 --out
#   조건: 프로덕션 빌드 + next start · 390×844 · 콜드 캐시 · 3회 중앙값 · 4G(4Mbps↓/RTT 70ms/CPU 4x)
#   정본: docs/audit/PERF-THROTTLED-4g.md (perf 트랙 커밋 3d3d128c)

# 그 사이에 무엇이 있는가 (소스)
sed -n '482,490p' components/tour-mode/guide/GuideConsole.tsx
```

### 수정 아님 — U9 후보

고칠 때 건드릴 자리는 `preShell` 하나다. 다만 **`preShell` 은 에러 메시지도 그린다**(`접근할 수 없어요`) —
에러에 스켈레톤을 씌우면 영원히 로딩 중인 화면이 된다. **로딩과 에러를 갈라야** 한다.

## UX-002 — 컨시어지: 13초를 치르고 실패했는데, 「다시 시도」할 것이 없다

**축:** R(응답성) · H(위계) · **판정: 합격선 위반 + 문구가 지키지 못하는 약속**

### 증상

성능 트랙 P-07: 질문 → 답변 **9~13초**(예산 2~3배), **게다가 실패**.
원인은 그쪽 원장에 있다(라우터 타임아웃 8s × 공급자 2 vs 예산 4s). **여기서는 그 13초가 손님에게 어떻게 보이는가만 본다.**

| 구간 | 손님이 보는 것 | 소스 |
|---|---|---|
| 0 → 13초 | `<span>확인 중…</span>` **문자열 한 줄** | `ConciergePanel.tsx:286` |
| 13초 | 「문제가 발생했어요 — **다시 시도하거나** 가이드에게 물어보세요.」 | `concierge.ts:201` |
| 그 다음 | **누를 것이 없다.** 질문을 다시 타이핑해야 한다 | 재시도 어포던스 **0건** |

### 🔴 진짜 결함은 문구가 아니라 문구가 지키지 못하는 약속이다

**실패 문구 자체는 잘 쓰였다.** 실패를 숨기지 않고, 다음 행동 둘(재시도 · 가이드에게)을 준다 —
A8 감사가 S5(회복력)를 올린 그 작업의 결과다.

**그런데 「다시 시도」할 버튼이 없다.** `grep -cE 'retry|다시 시도|재시도' ConciergePanel.tsx` → **0**.
13초를 기다린 손님에게 "다시 시도하세요"라고 말하면서 **다시 시도하는 방법은 타이핑을 처음부터**다.
투어 중, 걸으면서, 한 손으로.

### 곁가지 — 실패가 정상 답변과 같은 모양으로 들어간다

`ConciergePanel.tsx:140` — `push('assistant', copy.error)`.
`ThreadEntry` 는 `{ id, role: 'user' | 'assistant', text, mapCard?, diningCard? }` 로 **에러 플래그가 없다.**
실패는 **일반 어시스턴트 버블**로 렌더된다.

⚠ **이걸 단독 결함으로 올리지 않는다.** 채팅 UI 가 시스템 메시지를 버블로 주는 건 정당한 관용구이고,
문구가 스스로 실패라고 밝힌다. 다만 **재시도 버튼을 붙이려면 이 플래그가 먼저 필요**하므로 같이 적어 둔다.

### 재현

```
# 시간 (성능 트랙)
node scripts/qa-perf-interactions.mjs --runs 10     # P-07
# 무엇이 보이는가 (소스)
sed -n '284,290p;138,142p' components/tour-mode/ConciergePanel.tsx
grep -n "thinking:\|error:" lib/tour-room/concierge.ts
grep -cE 'retry|다시 시도|재시도' components/tour-mode/ConciergePanel.tsx   # → 0
```

## UX-003 — 패턴: 기다림을 문자열로 때우는 것이 이 앱의 기본형이다

**축:** C(일관성) · **판정: UX-D6 위반이 산발이 아니라 기본형**

두 건이 독립적으로 같은 모양이었다:

| | 기다림 | 그 동안 보이는 것 |
|---|---|---|
| UX-001 가이드 콘솔 | 1,778 ms | `<p>불러오는 중…</p>` |
| UX-002 컨시어지 | 9,000~13,000 ms | `<span>확인 중…</span>` |

**두 번이면 우연이지만, 인구조사가 이미 셋을 말하고 있었다** — 스켈레톤 13파일 · 스피너 15 · **로딩 문자열 21**.
문자열이 **최다 관용구**다. UX-D6(«스켈레톤이 기본, 문자열 단독 금지»)은 소수를 다수로 바꾸는 결정이다.

🔴 **U3 이 이걸 표면별로 세어야 한다.** 지금 숫자(21파일)는 **소스 기준이라 상한**이다 —
그중 몇 개가 실제로 500ms 넘는 기다림에 걸리는지는 렌더만 안다. 190 hex 중 84가 SVG였던 것과 같다.

## UX-004 — 스킨 스와치가 테마 토큰을 손으로 베껴 적은 표다

**축:** C(일관성) · **판정: 정본 이원화**

`SkinPicker.tsx:147-157` 의 `SWATCH` 표는 10개 스킨의 `canvas`·`bubbleIn`·`bubbleMe`·`hill` 색을
**hex 리터럴로 다시 적어 둔다.** 정본은 `app/tour-room-theme.css` 의 `data-tr-skin` 블록이다.

**실측 대조 — 5/5 정확히 일치한다:**

| 스킨 | `--tr-canvas` (CSS) | `SWATCH.canvas` |
|---|---|---|
| sky | `#b9cddd` | `#b9cddd` |
| winter | `#dde8f2` | `#dde8f2` |
| forest | `#e4e8cd` | `#e4e8cd` |
| jeju | `#e9f5ea` | `#e9f5ea` |
| busan | `#cfe7f0` | `#cfe7f0` |

🔴 **오늘 일치한다는 게 문제다.** 값이 맞으니 아무도 안 본다. 스킨 하나의 토큰을 고치는 순간
**미리보기만 옛 색을 보여 주고, 게이트는 아무 말도 안 한다.** 이 트랙의 지배 결함 유형 그대로다 —
만드는 문제가 아니라 **이어 두지 않은 문제**이고, 단위 테스트로는 안 잡힌다.

**토큰 우회 104건 중 39건이 이 표 하나다.** 나머지 65건과 성격이 완전히 다르므로 따로 센다 —
65건은 "토큰을 안 썼다", 39건은 **"토큰을 베꼈다"** 이다. 후자가 더 위험하다.

**재현:** `sed -n '146,158p' components/tour-mode/SkinPicker.tsx` · `grep -A12 "data-tr-skin='sky'\]" app/tour-room-theme.css`

**U9 방향(수정 아님):** 스와치를 CSS 변수에서 읽거나(`getComputedStyle`), 토큰을 JS 로 내보내 양쪽이
한 곳을 읽게 한다. 표를 지우는 게 아니라 **표의 출처를 바꾸는** 일이다.

### UX-005 — 투어 제목이 **네 표면 전부**에서 잘린다

`h1.tr-title truncate` — 실제로 `scrollWidth > clientWidth` 가 발동했고 `.text-cjk-safe` 도 아니다.
보이는 것: **"Pocheon: Lake, Herb Island &"** 에서 끝.

G-i 는 이걸 **손님 헤더 문제**로 적어 뒀다. **아니었다** — 손님 홈·손님 채팅·가이드 콘솔·콕핏 **4/4** 다.
같은 `h1` 이 모든 셸에 있고, 우측 아이콘들과 폭을 다투는 구조도 같다.
**한 곳을 고치면 네 곳이 고쳐진다**(반대로, 지금까지 아무도 안 고쳤다는 뜻이기도 하다).

### UX-006 — 손님 화면엔 **이길 것이 없다**

`--tr-accent` = `#2e5e4e`. 그 배경을 가진 가시 컨트롤 수:

| | primary |
|---|---|
| 손님 홈 (컨트롤 13) | **0** |
| 손님 채팅 (29) | **0** |
| 가이드 콘솔 (11) | 1 — `drive-hero` |
| 콕핏 (21) | 1 — `driver-mic` |

손님 홈의 13개 중 배경이 있는 건 4개(전부 `rgb(252,252,251)` 근백색), 나머지 9개는 완전 투명이다.
**스태프 표면은 위계가 있고 손님 표면은 없다.** G-f("타일 7개 중 5개가 동일한 차콜")가
파스텔 팔레트로 바뀌었을 뿐 병은 그대로다.

🔴 **합격선을 「≤1」에서 「정확히 1」로 고쳤다**(UX-D12). primary 가 없는 화면은 셋 있는 화면만큼 나쁘다 —
전자는 이 계측 없이는 **초록으로 보인다.**

**관제도 0이다** — 컨트롤 18개 중 accent 배경 **0개**. UX-D3 에서 관제를 「C+H 두 축」으로 잡은 판단이
여기서 값을 했다. **일관성 축만 봤으면 이 화면은 통과했을 것이다** — 토큰은 잘 쓰고 있고, 잘림도 0이고,
하단 가구도 8% 다. **문제는 "규칙을 어겼다"가 아니라 "아무것도 이기지 않는다"** 이고,
그건 위계 축으로만 보인다. G-l(SOS 가 룸 개수와 같은 무게)이 같은 병의 더 심한 형태다.

### UX-007 — 콕핏 하단 가구 31%

`driver-quick-replies h=50` + `h=51` + `h=157` = **258px / 844 = 31%**(합격선 25%).
운전 중에 보는 화면에서 아래 1/3이 고정 가구다.

### ✅ 해소 확인 — G-g(채팅 하단 330px)는 이제 합격이다

실측 **172px = 20%**(컴포저 블록 115 + 탭바 57). G-g 가 적은 330px 은 `#548`(스마트가이드 카드 제거) 이전 값이다.
**UX-D1 에서 "합치지 않는다"고 판단한 근거가 실측으로 확인됐다** — 밀도는 이미 합격선 안이므로
오발신 위험을 무릅쓰고 시그널·퀵리플을 합칠 이유가 없다.

### ✅ P축은 깨끗하다 — 그리고 소스의 43은 결함이 아니었다

네 표면 전부 **44px 미만 히트 타깃 0**. U2 가 소스에서 센 40~43px 지정 **43건**은
**"렌더로 확인할 후보 상한"이라고 적어 둔 그대로**였다 — 실제 히트 타깃이 아니었다.
(다른 상태·표면에서 다시 볼 것. 지금 결론은 "이 네 화면엔 없다"이지 "앱에 없다"가 아니다.)

### 🔴 이 계측기는 다섯 번 틀린 뒤에 맞았다

D축 하나가 다섯 판을 갔고, **매번 다른 방향으로 틀렸다.** 기록해 둔다 — 다음 계측기도 그럴 것이기 때문이다.

| 판 | 규칙 | 보고한 값 | 무엇이 틀렸나 |
|---|---|---|---|
| 1 | `position: fixed/sticky` 를 찾는다 | 손님 **0px** | 이 앱엔 fixed/sticky 가 **하나도 없다.** 하단 스택은 **플렉스**로 만든다 — 결과가 아니라 **기법**을 찾았다 |
| 2 | 뷰포트 바닥에 붙은 요소 | 채팅 **57px** | 탭바만 봤다. 컴포저는 바닥이 787 이라 안 걸린다 |
| 3 | 위로 체이닝 | 전 표면 **100%** | 본문 영역(`tr-atmos h=735`)까지 삼켰다 |
| 4 | 요소 높이 30% 상한 | **35%** | 풍경화 SVG 의 `<path>` 한 조각(h=240)을 가구로 셌다 |
| 5 | SVG·아트 레이어 제외 | **7 / 20 / 7 / 31%** | ✅ |

**1판이 가장 위험했다** — 0px 은 «합격»으로 보인다. 도달 단언이 없었다면 그대로 초록으로 넘어갔다.
그리고 **4판의 오탐은 C축이 이미 가르쳐 준 것과 같은 것**이었다(190 hex 중 84가 풍경화).
**아트 레이어는 축이 바뀌어도 계속 끼어든다.**

🔴 **그리고 이 하니스는 한 번, 예약이 사라진 DB 를 상대로 "컨트롤 13개 · 위반 0"을 보고했다.**
화면엔 「해당 정보의 예약을 찾을 수 없습니다」가 떠 있었다. 도달 단언(`controls < 5` → unreachable, exit 2)을
넣은 이유다. **0 을 보고하는 게 가장 위험한 실패다.**

### ⚠ 시뮬은 공유 자원이다

측정 중 시뮬 예약 3건이 **DB 에서 사라졌다**(`sim_tag` 행 0). `sim-tour-day.ts --cleanup` 은
**파일이 아니라 `sim_tag` 로 지우므로 상대 세션 것까지 같이 지운다.**
성능 트랙과 동시에 돌릴 수 없다 — **시딩 전에 알리는 것이 규칙이어야 한다.**

**재현:** `ALLOW_SIM_SEED=1 npx tsx scripts/sim-tour-day.ts` → `WALK_BASE=http://localhost:3181 node scripts/qa-uiux-render.mjs`
