## P-01 🔴 룸 진입이 4G 성능 예산을 넘는다 — §F #4 최초 실측, 미달

**증상.** 손님이 초대 링크를 열고 실제로 쓸 수 있게 되기까지 **4G에서 2.9~3.2초**.
§F 예산은 **< 2.5s (4G)** 다. 이 지표는 그동안 **한 번도 측정된 적이 없었다**
(`A0-perf-baseline.md` 가 "미측정 6/10" 로 남겨둔 항목).

| 라우트 | 4G 첫 유의미 | 예산 | 판정 | slow4g 첫 유의미 |
|---|---|---|---|---|
| 룸(진행 중 투어) | **2,909 ms** | 2,500 ms | ❌ **+409 ms (16% 초과)** | **5,553 ms** |
| 룸(로비, D-1) | **3,164 ms** | 2,500 ms | ❌ **+664 ms (27% 초과)** | **5,454 ms** |
| 가이드 콘솔 | 2,454 ms | (예산 없음) | — | 4,929 ms |

[실측] 3회 중앙값 · `scripts/qa-perf-throttled.mjs`

🔴 **연결이 나빠지면 선형이 아니라 2배로 나빠진다** — 4G 2.9초 → slow4g **5.6초**(1.9배).
JS 페이로드가 지배적일 때 나타나는 모양이다(대역폭이 절반이면 다운로드가 두 배).
제주 시골 구간·버스 이동 중이 정확히 slow4g 쪽이고, 예산의 근거가
*"버스 하차 직전 30초 안에 정보 확인"* 이므로 **실사용에서 더 나쁜 쪽이 기본값에 가깝다.**

**분해 — 병목은 서버가 아니라 전부 클라이언트다.**

| 구간 | 룸(live) | 읽는 법 |
|---|---|---|
| TTFB | **7 ms** | 서버는 즉답한다. 여기엔 문제가 없다 |
| FCP | 2,832 ms | 첫 픽셀까지 2.8초 — **이 구간이 사실상 전부** |
| 첫 유의미 | 2,909 ms | FCP 직후 바로 사용 가능해진다 |
| LCP | 3,548 ms | 최대 요소는 더 늦다 |

**TTFB 7ms → FCP 2,832ms.** 그 사이에 서버 작업은 없다. 오직 **612 KB JS 의 다운로드·파싱·실행**과
그 뒤의 `join` 왕복뿐이다 [실측 + 코드 실측].

**원인 (코드 실측).** `app/(app)/tour-mode/room/[bookingId]/page.tsx` 는 `force-dynamic` 인데
**서버에서 데이터를 하나도 읽지 않고** `TourRoomClient` 만 렌더한다. 즉 손님은
**HTML → JS 다운로드 → 파싱/실행 → join API → snapshot → 렌더** 를 **직렬로** 기다린다.
서버가 7ms 에 답할 수 있다는 것은, 그 시간에 스냅샷을 같이 실어 보낼 여지가 있다는 뜻이다.

**영향.** 손님 전원. 그리고 §F 예산의 근거가 *"버스 하차 직전 30초 안에 정보 확인"* 이므로
이 초과는 실사용 시나리오를 직접 침해한다.

**게이트 가능:** ✅ `qa-perf-throttled.mjs --check` 로 예산 게이트화 가능(현재 `--check` 미구현, P6).

## P-06 🔴 성능 아님 — 차량이 배정된 예약은 **삭제가 구조적으로 불가능하다**

성능 감사 중 시뮬 드레인이 실패하면서 드러났다. 성능 문제가 아니라 **데이터 무결성 결함**이라
여기 적어 두고, 수정은 이 트랙 밖이다.

**스키마 (라이브 실측, `pg_constraint`):**
```
ops_room_vehicles_anchor_present   CHECK (group_id IS NOT NULL OR room_id IS NOT NULL)
ops_room_vehicles_room_id_fkey     FOREIGN KEY (room_id)  → tour_rooms(id)      ON DELETE SET NULL
ops_room_vehicles_group_id_fkey    FOREIGN KEY (group_id) → ops_tour_groups(id) ON DELETE CASCADE
tour_rooms_booking_id_fkey         FOREIGN KEY (booking_id) → bookings(id)      ON DELETE CASCADE
```

**체인:** `bookings` 삭제 → CASCADE → `tour_rooms` 삭제 → `ops_room_vehicles.room_id` **SET NULL** →
그 행은 `group_id` 도 NULL 이라 **CHECK 위반** → 트랜잭션 롤백 → **예약 삭제 전체가 실패한다.**

**즉 룸에 차량이 배정된 예약은 지울 수 없다.** 방-앵커 차량(`group_id` NULL, `room_id` 있음)은
전세/프라이빗 투어의 정상 형태다.

**실제 발생:** 오늘 `sim-tour-day.ts --cleanup` 이 이 제약으로 **exit 1** 로 죽었다 [실측].
에러 원문: `new row for relation "ops_room_vehicles" violates check constraint
"ops_room_vehicles_anchor_present"`. 문서화된 드레인 경로가 막힌 것이므로
**이 함정은 시뮬을 쓰는 다음 세션마다 재발한다.**

**영향:** 예약 취소·삭제 경로 · 개인정보 삭제 요청(GDPR 식) · 시뮬 드레인.
현재 `ops_room_vehicles` 총 2행뿐이라 운영 폭발이 안 났을 뿐이다 [실측].

**우회(오늘 쓴 것):** 해당 `ops_room_vehicles` 행을 먼저 지우고 드레인 재실행 → 성공
(15건 제거 · 잔여 0 · 고아 0). ⚠ 사장님의 `manual-test-2026-07` 11건은 건드리지 않았다(확인함).

### ✅ 수정 완료 (2026-08-03, 사장님 승인 후 라이브 DDL)

🔴 **처음 제안한 "`room_id` 를 ON DELETE CASCADE 로" 는 틀렸다.**
라이브에 **`group_id` 와 `room_id` 를 둘 다 가진 행이 실재한다** [실측]. 그 행은 룸이 사라져도
그룹 앵커로 유효하고 지금은 정상 생존한다(room_id 만 NULL). 통짜 CASCADE 는 **그것까지 지워
현재 동작을 퇴행**시킨다. FK 액션으로는 "앵커가 이것 하나뿐일 때만"을 표현할 수 없다.

**적용한 것** (`supabase/migrations/20260803120000_room_vehicles_deletable.sql`):
`tour_rooms` 에 **BEFORE DELETE 트리거** — 그 룸에만 매인(`group_id IS NULL`) 배정만 함께 지운다.
이중 앵커 행은 기존 FK `SET NULL` 경로로 그대로 생존한다. CHECK 는 손대지 않고 위반 상황만 없앤다.

**검증** [실측]:
| 확인 | 결과 |
|---|---|
| 실패했던 경로 재실행(`sim-tour-day` 시드 → `--cleanup`) | **exit 0** (이전 exit 1) |
| 이중 앵커 행 생존 | ✅ 사장님 `manual-test-2026-07` 행 무사(room·group 둘 다 유지) |
| 어드바이저 재실행 | 🔴 **내 변경이 새 지적을 만들었다** — `anon_security_definer_function_executable`. 트리거 함수가 PostgREST 로 노출됨 → `revoke execute` from public·anon·authenticated 적용 → **재실행 시 0건** |
| 회수 후에도 트리거 동작 | ✅ 시드→드레인 다시 exit 0 |

**게이트:** ⚠ **구조 검사는 못 붙였다.** `qa-ops-center-queries.ts` 에서 `pg_trigger` 를 읽으려면
raw SQL 이 필요한데 이 레포엔 범용 SQL RPC 가 없다(DDL 은 전부 MCP 수동 경로).
**행동 게이트는 시드→드레인 사이클**이다 — 회귀하면 `sim-tour-day.ts --cleanup` 이 **exit 1** 로 죽는다.
시뮬을 쓰는 세션마다 밟는 경로라 실효는 있으나 **CI 자동 게이트는 아니다.**
🔴 마이그레이션 파일 존재로 검증하지 말 것 — **레포에 있다 ≠ 적용됐다.**

## P-07 🔴 컨시어지 Tier1 — 예산 4초짜리 기능이 공급자 하나당 8초를 기다리게 돼 있다

**실측 (LLM 실호출 3회, 사장님 승인):**
| # | 응답시간 | 결과 |
|---|---|---|
| 1 | **13,078 ms** | HTTP 500 |
| 2 | 8,952 ms | HTTP 500 |
| 3 | 9,077 ms | HTTP 500 |

`[ai-router] openai/gpt-5-mini rejected "temperature" — retrying without it` — 왕복이 한 번씩 더 든다.

⚠ **이 실패가 프로덕션에서도 나는지는 확정 못 했다.** 로컬 `.env.local` 에 `GEMINI_API_KEY` 는

**단 타임아웃 산수(8s × 2 vs 예산 4s)는 환경과 무관하다.**
→ 프로덕션 확인 필요. 판정 수단은 이미 있다: `ops_ai_usage` 조회.

**영향:** 손님이 질문하고 **9~13초 기다린 뒤 아무것도 못 받는다.** §F 예산의 근거가
*"그 이상이면 손님이 가이드에게 물어본다"* 인데, 이건 물어볼 시간마저 뺏는다.

**게이트 가능:** ✅ `timeoutMsFor('concierge') <= §F 예산` 을 강제하는 단위 테스트.
예산과 타임아웃이 **한 소스를 읽게** 만들면 다시 어긋나지 않는다.

## P-08 상호작용 예산 — #5 통과, #6 은 **첫 탭만** 초과

[실측] CPU 4x 스로틀 · 네트워크 무스로틀(옵티미스틱 성질 검증 목적) · n=12 · `qa-perf-interactions.mjs`

| §F 지표 | 예산 | 첫 회 | warm p50 | 판정 |
|---|---|---|---|---|
| #5 메시지 전송 → 화면 반영 | 300 ms | 22~33 ms | **16.7~19.9 ms** | ✅ **PASS** (여유 10배 이상) |
| #6 카드 탭 → 시트 열림(서랍) | 150 ms | **334~349 ms** | **17.6~22.6 ms** | ❌ **첫 탭만 FAIL** (2.2~2.3배) |

🔴 **n 이 작을 때 p95 를 그대로 읽으면 오독한다.** #6 의 p95 는 사실상 **첫 회 그 자체**다.
두 번째부터는 ~20ms 로 예산의 1/7 이다. 즉 **"서랍이 상시 느리다"가 아니라 "첫 탭이 느리다"** 이고,
원인은 지연 로드되는 1회성 비용으로 보인다(코드 스플릿·이미지 — 미확정, P5 에서 프로파일 필요).
손님은 그 첫 탭을 **한 번은 반드시** 겪는다.

⚠ **재현성 확인함(중요).** 한 번은 첫 회가 **149.7ms** 로 나와 통과처럼 보였다. 그 값을 믿을 뻔했으나
**콜드 컨텍스트로 6회 반복하니 348.9 · 341.1 · 334.0 · 336.6 · 344.2 · 341.9** 로 촘촘했다 —
**149.7 이 이상치**다. 단발 측정으로 예산 통과를 선언하지 말 것.

#### 어느 표면 · 어느 상호작용 · 몇 번 (UI/UX 트랙 U5 흐름 감사용)

| 항목 | 값 |
|---|---|
| 표면 | **손님 룸** (`/tour-mode/room/[id]`) — 스태프 표면 아님 |
| 상호작용 | 홈 탭의 **서랍 열기**(`room-drawer-open` → `room-drawer`) |
| 조건 | CPU 4x 스로틀 · 네트워크 무스로틀 · 콜드 컨텍스트 |
| **빈도** | 🔴 **룸 세션당 1회** — 아래 실측 |

🔴 **첫 열기 비용은 되돌아오지 않는다 [실측].**
같은 컨텍스트에서 `[콜드 → warm → 탭 왕복(홈→채팅→홈) → 재열기]`:
**342.4 ms → 24.0 ms → 28.5 ms.**
탭을 옮겼다 돌아와도 warm 이 유지된다 ⇒ **스톱마다 겪는 비용이 아니라 룸 진입당 한 번**이다.
따라서 심각도는 "매번 340ms 느림"이 아니라 **"룸에 들어와 서랍을 처음 열 때 한 번 340ms"** 다.
(빈도가 판정에 들어가는 UI/UX 트랙 요청에 대한 답이다.)

## P-09 라우트 p50/p95 (#10) — 부분 측정에 그침, 원인은 픽스처

[실측] 브라우저 세션 내 fetch · 7회 · 로컬 프로덕션 서버 · 네트워크 스로틀 없음

| 라우트 | 상태 | p50 | p95 |
|---|---|---|---|
| `dietary` | 200 | **70 ms** | 80 ms |
| `extras` | 200 | **101 ms** | 113 ms |

나머지 13개는 **2xx 가 아니다** — `405 GET 미지원` 4건(approach·captions·dining·morning-briefing 은 POST 전용) ·
`404` 6건(messages·my-seat·plan·region-scripts·tour-itinerary·vehicle-eta — 시뮬 예약에 그 데이터가 없다) ·
`403` 2건 · `400` 1건.

🔴 **비-2xx 응답시간을 라우트 성능으로 적지 않는다.** 초판 하니스는 `x-tour-room-auth` 헤더를
몰라서 전 라우트가 403 이었는데 **숫자는 멀쩡히 나왔다**(40~60ms) — 그대로 실었으면
"손님 라우트는 전부 40ms대"라는 **정반대 결론**을 낼 뻔했다. 앱은 쿠키가 아니라 이 헤더로 인증한다.

**막는 것:** 더 두꺼운 픽스처(일정 확정·좌석·지역 스크립트가 들어간 방). `k4-seed.ts` 20방이 후보.
