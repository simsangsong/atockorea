## 타당성 — 예상보다 쉬웠다

원장에 *"초대 토큰이 URL 에 있고 `history.replaceState` 로 지우는 구조라 설계 결정 필요"* 라고
적었는데, **그 걱정은 과했다.** 같은 디렉터리의 `app/(app)/tour-mode/driver/page.tsx` 가
**이미 서버에서 `?rt=` 를 `verifyRoomToken` 으로 검증**하고 있다. 패턴이 이미 있었다.

프로토타입(집합 시각·장소를 서버가 먼저 그리는 카드)은 **작동했다**:

| 확인 | 결과 |
|---|---|
| `tsc` · `npm run build` | 0 · 0 |
| 서버 HTML 에 카드 포함 | ✅ (`room-ssr-first-screen`) |
| HTML 크기 | 15.1 → **18.4 KB** (+3.3) |

**계산상 효과**(측정 아님): 4 G 4 Mbps 에서 JS 622 KB 는 전송만 **약 1.2 초**다.
서버 HTML + 렌더 블로킹 CSS 48 KB 는 그 1/13 이라, **읽을 것이 2 초 이상 먼저 보인다.**
§F 예산의 근거가 *"버스 하차 직전 30초 안에 **정보 확인**"* 이므로 방향도 맞다 —
그 순간 손님에게 필요한 것은 **탭이 아니라 읽기**다.

## 🔴 그런데 넣을 데이터가 없다 (라이브 실측)

| 항목 | 실측 |
|---|---|
| `pickup_point_id` 가 있는 예약 | **0 / 34** (실예약 18 포함) |
| OTA 원문에 픽업 **장소** | **없음** (키 13종 중 장소 관련 0) |
| OTA 원문의 `pickup_time` | 있음 — **그런데 16건 전부 `"08:00"`** |
| 방이 생긴 실예약 | **3 / 18** |
| `tour_day_plans` | **1** 건 |

**`pickup_time` 이 결정타다.** 값이 있으니 카드는 렌더되는데, **16건이 전부 같은 값**이다.
예약별 사실이 아니라 **일괄 임포트 기본값**이다. 이대로 내보내면 **모든 손님이 자기 집합
시각으로 `08:00` 을 본다** — 빈 카드보다 나쁘다. 빈 화면은 모른다고 말하지만, 이건 **틀린 것을
안다고 말한다.**

장소를 빼고 시각도 못 믿으면 남는 것은 **투어 이름과 날짜**뿐이고, 그건 손님이 이미 안다.
⇒ **카드에 넣을 것이 없다.**

## 판정

**하지 않는다. 되돌렸다** (`git status` 깨끗, `tsc` 0).

- **기법은 유효하다.** 다시 하고 싶어지면 이 문서의 타당성 절과 `driver/page.tsx` 패턴이 출발점이다.
- **막는 것은 코드가 아니라 데이터다.** 픽업 장소가 0건이고 시각이 상수인 한, 서버가 먼저 그려도
  그릴 것이 없다.
- 🔴 이건 기능 감사 트랙의 결론과 같은 자리다 — *"최대 발견은 코드가 아니라 배달"*.
  **P-01 은 렌더링 문제로 보였지만 실제로는 운영 데이터 문제에 걸려 있다.**

## 그래서 P-01 을 실제로 닫으려면

**선행(코드 아님):** 예약에 **픽업 장소**가 들어가야 하고, `pickup_time` 이 **예약별 실제 값**이어야
한다. 지금은 둘 다 없다. 이건 임포트/운영 쪽 일이다.

**그 다음(코드):** 위 프로토타입을 되살린다 — 반나절 일이고 위험도 낮다(토큰 검증 패턴 존재,
실패는 조용히 `null`, 임계 경로에 인덱스 조회 1회).

⚠ **그리고 지표를 같이 고쳐야 한다.** 현재 `첫 유의미` 는 셀렉터가 DOM 에 나타난 시각이라
**"보이는데 안 눌린다"를 이미 도착으로 센다.** 서버 카드를 넣으면 그 지표는 ~400 ms 로 떨어지는데
**상호작용은 여전히 하이드레이션을 기다린다.** 그대로 두면 **지표만 좋아지고 손님은 그대로**다.
UI/UX 트랙의 헛탭 계측(`{taps, wasted, firstSeenAt, landedAt}`)이 정확히 그 구분을 한다 —
되살릴 때 그 계측을 같이 붙여야 자기 자신을 속이지 않는다.
